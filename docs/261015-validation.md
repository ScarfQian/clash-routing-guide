# 验证、排错与恢复

日期：2026-10-15；创建人：项目维护者。

## 分清四种结果

| 结果 | 能说明什么 | 不能说明什么 |
| --- | --- | --- |
| 单元测试通过 | 通用变换在虚构案例中的行为符合预期 | 你的订阅一定兼容 |
| Mihomo -t 通过 | 内核能解析候选及其引用资源 | 节点可达、认证成功、真实出口正确 |
| 真实请求成功 | 这次请求的链路可用 | 所有请求、所有时间都可靠 |
| DNS 检测结果 | 测试域名所见的递归解析器 | 其他域名、所有应用、真实客户端 IP 都没有泄漏 |

## 隔离演练

先运行 `npm run demo`。四个生成文件都在 `local/demo/`，使用虚构的普通节点和静态 provider。

使用自己已有的 Mihomo 二进制逐一执行：

```text
mihomo -t -d <项目的local/demo目录绝对路径> -f <local/demo/demo-basic.json的绝对路径>
mihomo -t -d <项目的local/demo目录绝对路径> -f <local/demo/demo-static.json的绝对路径>
mihomo -t -d <项目的local/demo目录绝对路径> -f <local/demo/demo-dns.json的绝对路径>
mihomo -t -d <项目的local/demo目录绝对路径> -f <local/demo/demo-auto.json的绝对路径>
```

尖括号是占位说明，执行时替换并按系统正确引用路径。`-t` 只检查配置；不要省略它来启动占用端口的第二个实例。演练不用真实订阅，不应安装证书或进行 HTTPS 解密。

实测自己的订阅时，将生成的脚本应用到独立候选副本，通过客户端的配置预览/校验核对增强顺序；不要将真实副本上传。模板没有 YAML 解析依赖，项目自测不能代替客户端对自己配置的完整生成。

检查每份候选：主入口和节点存在、没有重复组或循环、原订阅应用专用规则保留、GPT 与直连优先级正确、默认出口指向预期组。重新运行扩展应得到一致结果。原配置复杂到无法识别时先停止设计，不强行降级直连。

## 应用后的实际检查

| 测试对象 | 操作 | 看什么 |
| --- | --- | --- |
| 本地网关 | 发送一条简短请求 | 应用先连本地回环；网关上游另外核对 |
| GPT | 发短请求，查看 Clash 连接详情 | 目标域名和最终节点符合 GPT 组选择 |
| 普通网页 | 打开通用公网 IP 检测页 | 当前普通出口；它不证明 GPT 的出口 |
| 直连服务 | 检查同步状态、打开现有网页 | DIRECT 与预期可达性；进程名须按系统实测 |
| 静态主备 | 维护时段逐个单独确认 | 可达性和公网出口；主备 IP 可能不同 |
| 更新/切订阅 | 完成前述检查后逐份试 | GPT 组仍有效，普通入口随当前订阅，直连未丢失 |

一个 204 健康检查成功，只说明该 URL 的一次探测成功。最低探测延迟不等于最快模型首字速度，测速容差也不是绝对超时上限。原有流断开后需要重新请求，不能承诺零中断。

## DNS、IPv6 与 WebRTC

应用 DNS 候选后，重新运行自己浏览器中的 [BrowserLeaks DNS](https://browserleaks.com/dns) 或 [DNSLeakTest](https://www.dnsleaktest.com/)，记录时间并使用新的随机域名测试。检测页面显示的是本机浏览器的测试结果；别人代查网页返回的 IP 不是你的 IP。

观察到国内解析器不能直接证明真实 IP 暴露，也不能忽略：对随机代理测试域名，不能简单归因于其他后台直连应用。需要区分本机 DNS 旁路与代理远端解析。GPT 查询路径应结合 DNS 日志和连接数据单独核对。

DNS 列表里的 IPv6 地址是解析器地址；浏览器公网 IPv6 是另一项。IPv6 检测失败应标为未知。`dns.ipv6: false` 只影响该解析器对 AAAA 的回应，不能当作全机 IPv6 已关闭。

系统代理、Chrome 独立 DoH、内置解析器和 TUN 是不同层。macOS 对发往局域网 DNS 的自动接管存在限制，不能仅凭 TUN 开关宣布无旁路。后续若修改系统 DNS，先记录原设置，并验证关闭客户端时如何恢复解析。

WebRTC 保护只覆盖对应浏览器功能，完全禁用可能影响通话。语言、时区、定位是独立环境设置，不是 DNS 防泄漏证明，不要求为本项目修改它们。

## 常见问题

| 现象 | 先检查 |
| --- | --- |
| 本地网关 502 | 本机监听是否存在、回环是否绕过代理；不要先换云端账号 |
| EOF / SSE 中断 | 当前连接是否被切换/重载中断、上游是否主动关闭；保留错误时间与域名 |
| 上游 503 | 区分网关错误与服务端错误，不仅凭域名或套餐推断原因 |
| 静态备用 Error | 备用认证/连接没有验证成功，不能宣称已具备故障切换 |
| 切订阅后找不到组 | 原主入口变化、增强顺序或旧选择缓存；先回退再修候选 |
| DNS 测试没变化 | 候选是否应用、浏览器/系统是否接入、检测是否使用旧结果 |

## 恢复顺序

1. 恢复本次改动前的全局扩展和必要节点文件；通过客户端支持的方式保存/重载。
2. 恢复原订阅和线路选择。不要整包覆盖正在运行的客户端状态文件。
3. 若改过系统/Chrome DNS 或 TUN，逐项恢复；本项目工具自身不改这些设置。
4. 再检查本地网关、普通网页和 GPT 短请求。恢复可用后再研究候选问题。

参考：[Mihomo DNS](https://wiki.metacubex.one/config/dns/)、[TUN 与 DNS 接管](https://wiki.metacubex.one/config/inbound/tun/)、[Chrome 安全 DNS](https://support.google.com/chrome/answer/10468685?co=GENIE.Platform%3DDesktop)。
