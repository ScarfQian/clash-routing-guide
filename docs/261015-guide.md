# 按步骤完成自己的分流设计

日期：2026-10-15；创建人：项目维护者。

## 第 1 步：填目标表，不先改设置

复制下面的表到自己的本地笔记，不必发布。

| 对象 | 想要的出口 | 查询域名走哪里 | 出口失效怎么办 |
| --- | --- | --- | --- |
| GPT / OpenAI | 自己的静态出口，或先跟随订阅 | 最终与该业务线路配套 | 提示失败，手动切回订阅；不静默直连 |
| 普通默认流量 | 当前订阅，或其地区自动组 | 配套的加密 DNS | 按所选自动组或订阅处理 |
| 云同步 | 自行决定是否直连 | 配套直连解析 | 检查客户端与网页分别是否可达 |
| 学术资源 | 按机构权限和网络决定 | 与访问线路配套 | 先核对权限、校网和域名，不猜测代理问题 |
| 本地网关 | 本机回环 | 本地处理 | 检查进程及监听端口 |

固定出口、美国节点、家庭网络三个概念不同。一个名字带「住宅」的节点不证明 IP 固定，也不证明供应商的任何隐私承诺。主备节点也可能对应不同公网 IP。

没有静态出口也能开始：默认将 GPT 跟随当前订阅；以后添加自己的出口。DNS 服务本身不要求购买新代理。模板使用公共 DoH，但节点流量仍计入现有套餐。

**停点：目标未确定前，只填表。**

## 第 2 步：保存能恢复的原状

在客户端打开自己的配置/数据目录，保存以下内容到本地备份，勿上传：

- 全局扩展脚本与覆写；实际使用订阅的扩展文件。
- 当前订阅、模式、GPT 和普通代理组的选择。
- 当前系统 DNS、系统代理、TUN 状态、Chrome 安全 DNS 的实际开关及策略控制情况。
- 若需要修改静态节点文件，先备份该文件。

备份后读取副本，确认内容可用。配置中的凭据、系统路径、截图和诊断输出都可能识别个人。不要把客户端整个数据目录放进公开项目。

Chrome 偏好文件里缺少一个键，不能证明功能关闭。不要在客户端运行时直接覆盖它维护的订阅选择索引；恢复应按客户端支持的保存/重载机制进行。

**停点：备份未确认可恢复，不应用。**

## 第 3 步：生成自己的候选

推荐运行 `npm run guide`，按提示填写设计。也可把 `examples/design.example.json` 的内容复制到 `local/design.json` 后编辑。Windows 用户可直接用编辑器操作，不需要使用 Unix 的复制命令。

| 字段 | 填写方法 |
| --- | --- |
| subscriptionEntry | 订阅末尾 MATCH 指向的代理组；留空自动识别，失败时明确填写 |
| staticExit.enabled | 已有自己的静态节点时设为 true；没有就保留 false |
| staticExit.providerPath | 相对 Mihomo 数据目录的本地 provider 路径，不是仓库路径 |
| ordinary.mode | subscription 保留订阅入口；auto 仅为普通默认流量生成地区自动组 |
| ordinary.include / exclude | 按自己的节点命名筛选；如有倍率要求，明确写入表达式 |
| ordinary.interval / tolerance | 默认 300 秒和 100 毫秒；是起点，不是所有网络的最优值 |
| directServices | 选填 onedrive、icloud、publishers；未选则不新增对应直连 |
| extraDirectDomains | 额外直连域名后缀，例如自己的业务域名；只在本地填写 |
| extraGptHosts | 确认确需同出口的具体主机，按 DOMAIN 精确匹配 |
| dns.enabled | 第一轮保持 false，访问分流验收后再独立考虑 |

运行 `npm run build`，得到本地 `local/global-script.js`。生成不会修改 Clash。

### 静态节点放在哪里

在 **Mihomo 数据目录** 内自行创建 `proxy_providers/static.local.yaml`，内容格式参考 `examples/static-provider.example.yaml`。供应商提供 VLESS、HTTP、SOCKS 等何种协议，就使用其完整、正确参数；不要把 VLESS 凭据硬套进 SOCKS 示例。

示例节点不可联网。生成器不会索取或写入真实凭据，Clash 的全局脚本也没有文件读取 API；实际节点由 Mihomo file provider 读取。文件路径受内核数据目录约束。

静态出口独立于普通订阅，因此更新普通订阅不应替换静态节点。但自己主动更新静态供应商凭据时，仍需维护本地 provider 文件。

### 规则按什么顺序

本机回环 → 已选择的服务直连 → GPT 域名 → 原订阅规则 → 普通默认出口。原订阅的媒体等应用专用组继续保留，并不会全部被地区自动组替代。

不要用 DOMAIN-KEYWORD 的宽泛词把大量无关网站归入直连，也不要把共享的 Cloudflare、Stripe、WorkOS 全域默认归入 GPT。先观察真实请求，再添加必要的精确主机。

## 第 4 步：只在隔离文件中检查

运行 `npm run check` 和 `npm run demo`。再按照[验证文档](261015-validation.md)使用自己的 Mihomo 检查候选。

对每份准备使用的订阅检查入口是否存在、地区筛选是否为空、原应用规则是否保留。订阅使用 provider 且没有内联节点时，使用订阅自己的自动组，不启用本模板的内联节点筛选。

全局脚本可跨订阅重新生成，但不能保证未来所有订阅格式兼容。主入口无法识别时必须报错，不能静默选择 DIRECT。与其他全局/单订阅扩展叠加时，核对客户端增强顺序。

**停点：到这里仍可保持现有网络不动。**

## 第 5 步：再小范围应用

准备好恢复入口后，手动把候选脚本合并到客户端的全局扩展。已有全局脚本时不能直接覆盖，先比较其业务规则。不要编辑客户端自动生成的运行配置来实现长期规则。

继续使用规则模式。静态出口开启后，新 GPT 组首项是静态；没有静态出口则跟随普通线路。既有选择可能由内核缓存，应用后必须查看真实选择和连接。

先确认本地网关、GPT、普通网页、主动选择的直连服务均可用，再测试更新/切换另一份订阅。切换代理可能中断已有连接，健康检查不能把旧 TCP/SSE 流迁移到新节点。不要在重要上传或长回答中做切换试验。

## 第 6 步：单独处理 DNS

访问分流验收后，把本地设计中的 dns.enabled 改为 true，重新生成并隔离检查。

- GPT 的 DoH 请求显式经过 GPT 组；普通默认 DNS 显式经过普通组。
- 明确直连域名使用阿里 DoH；代理节点解析单独直连处理。
- DNS 服务自身用 IP 形式的加密入口启动解析，减少循环依赖。
- 这里会统一替换继承的 nameserver-policy/fallback；复杂 RULE-SET、GEOIP 或特殊内网解析须人工核对，不能宣称一套域名策略还原了所有路由语义。
- 本地域名暂交给 system；如果后来把系统 DNS 指回本机监听，必须同步设计局域网解析路径，避免回环。

这一步只管理进入 Mihomo 的查询，不会自动修改系统/Chrome DNS，也不会打开 TUN。代理远端自行做的解析也需单独判断。对「所有应用都无旁路」的目标，需要额外设计接管范围并实测。
