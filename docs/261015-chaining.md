# 链式出口：理解后再扩展

日期：2026-10-15；创建人：项目维护者。

## 三种容易混淆的设计

| 设计 | 真实路径 | 特点 |
| --- | --- | --- |
| GPT 直接选静态节点 | 电脑 → 静态代理 → GPT | 主模板支持；实际仍取决于节点供应商的内部网络 |
| GPT 跟随普通线路 | 电脑 → 当前订阅节点 → GPT | 主模板支持；不经过自己的额外静态代理 |
| 保留前段，再接静态出口 | 电脑 → 前段代理 → 后段静态代理 → GPT | 本文解释；主生成器不自动启用 |

多个 select 组嵌套不代表多个代理跳数。需要后段节点的 `dialer-proxy` 等机制，才明确要求通过前段建立连接。

## 为何不能简单再加一条域名规则

规则通常按顺序匹配并选择路径，后面的同域名规则不会自动接在第一条后面。实现链式出口需要新的后段节点，并为它指定前段拨号组。

如果 GPT 和普通流量要保留不同前段，再共享一个后段服务，应分别定义两个逻辑节点，拨号组分别指向 GPT 前段和普通前段，不能让一个节点同时拥有两条不同的 dialer-proxy。

先画出依赖：后段 → 前段。前段不得再引用后段或包含后段的选择组，否则形成循环。本机和明确直连服务仍应先按直连规则处理。

## 成本与边界

前段订阅和后段服务都可能计费；链式连接不会免除前段流量。最后一个代理通常决定网站看到的出口 IP，但不能因此保证匿名、账号可用、零延迟或流不中断。

供应商必须支持对应协议和连入方式。HTTP CONNECT、SOCKS、VLESS 的参数不通用；后段不可达或认证错误时，不能把它包装成已可用方案。

链式扩展先保存在本地候选，单独确认主备可达性、最终公网出口、DNS 路径和长连接行为，再提供明确开关。开关默认关闭，恢复入口应独立可用。
